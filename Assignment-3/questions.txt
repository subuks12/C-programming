(1) filter1 and filter2 do the same calculation, but they iterate through the image in a different order. filter1 loops with j as the outer loop and i as the inner loop, while filter2 loops with i as the outer loop and j as the inner loop. Because the pixels are stored in row-major order, filter2 accesses memory in a more cache-friendly order than filter1, even though both return the same count.

(2) The raw timing data from eval.sh is a list of measured times for each run, one value per execution. The plot uses the average of those repeated runs, so the curve is smoother than the raw numbers. The times vary a little from run to run because the system is doing other work in the background, but the variation is usually small compared to the overall timing values.

(3) The valgrind cachegrind output shows how many memory accesses are cache hits and cache misses for each program. The difference is caused by loop order: filter1 traverses the image in a way that jumps between distant memory locations, while filter2 accesses nearby pixels in sequence. Since the image is stored row by row, filter2 makes better use of the CPU cache and has fewer misses, so it runs faster. The timing difference comes from reduced cache misses and therefore less memory stall time.
