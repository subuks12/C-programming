(1) UDP can drop either a move request or its reply. The client retries requests after a timeout, and each move has a sequence number so the server does not apply a retried move twice. Clients also poll for the server's current game state, which lets them recover from a lost update or a server restart. Persistent packet loss can still delay play, and a server failure before a move is saved can lose that move.

(2) The save file is a raw binary copy of C structs, so it depends on the compiler's structure layout, integer representation, and machine byte order. Although writes are checked and synced, a crash during truncation or writing can leave a partial file and there is no atomic replacement, checksum, or format version. The server also stores UDP client addresses; recovery assumes the client processes and their sockets remain alive. A restarted client, corrupted save file, disk failure, or multiple server instances can prevent recovery or produce inconsistent state.
